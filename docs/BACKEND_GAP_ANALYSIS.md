# 观茶 P0 后端差距分析

> 审计日期：2026-08-04  
> 目标基线：《观茶｜黑客松 P0 后端研发 PRD v1.0》  
> 当前判断：后端需要按新合同建设；旧后端可定向迁移，不可原样接入

## 1. 执行结论

当前前端没有后端接入。`guancha-agent-v0.1` 是真实存在的旧 FastAPI/PostgreSQL 原型，但它的接口、图片模型、任务方式、数据不可变性和工程分层都与 2026-08-04 P0 合同有显著差异。

最稳妥的策略不是“完全忽略旧代码”，也不是“在旧代码上继续堆接口”，而是：

1. 以后端研发 PRD 的 `/api/v1`、OpenAPI 和数据版本原则建立新骨架；
2. 从旧项目只迁移通过审查的纯函数、测试样例、规则候选和 Provider 经验；
3. 不迁移旧路由结构、路由内 SQL、旧表命名和可变覆盖逻辑；
4. Obsidian 只作为可追溯知识来源，不作为应用数据库；
5. 买后茶仓和日记在 P0 继续本地保存，后端只承担反馈分析桥接。

## 2. 资产冲突与处理原则

| 来源 | 表述 | 本次处理 |
| --- | --- | --- |
| 完整机制 PRD v0.3 | 已有后端与数据库可复用 | 作为“存在候选资产”的事实 |
| 后端研发 PRD v1.0 | 本轮后端基本从零；旧代码只能先审计 | 作为研发执行约束 |
| 旧后端报告 | 多轮闭环、真实图片和评测曾通过 | 历史结果，需在当前环境重新验证 |
| Obsidian | 含产品字段、规则、证据、导出 | 只读候选资产，不是最终数据库 |

不得用历史投入或文件名中的“最终”“验收通过”替代当前合同测试。

## 4. 目标能力差距矩阵

| 目标能力 | 当前前端 | 旧后端 | 差距与结论 |
| --- | --- | --- | --- |
| `/api/v1` 版本化 | 无 API | 旧接口无 `/api/v1` | 必须新建版本化路由 |
| 匿名用户上下文 | 本地状态 | `user_id`/偏好快照雏形 | 缺 anonymous client、保留期和限额 |
| 1–5 候选 | 前端支持 5 个 Mock | 旧图片接口要求总共 2–3 图 | 模型和接口均不兼容 |
| 每候选 1–2 图 | 当前可到 4 | 旧接口按整批图片推断候选 | 必须改为候选级图片资源 |
| MIME/签名/5MB | 无 | 旧代码允许更多格式，能力不完整 | 必须按 JPEG/PNG 重做校验链 |
| 同候选多图联合抽取 | 无 | 旧接口按批次 Provider 抽取 | 需候选级联合调用和版本 |
| 不同候选并行、最大 3 | 无 | 未形成目标任务模型 | 需 TaskRunner 抽象 |
| 异步 Job 与轮询 | 固定 2.2 秒 | 旧接口多为同步组合调用 | 必须新增持久任务状态 |
| Evidence 三维模型 | 只有固定文案 | 旧字段/claims 有部分能力 | 缺信息/来源/核验三个正交维度 |
| ExtractionVersion | 无 | 旧表偏日志/覆盖字段 | 必须不可变追加 |
| DecisionVersion/Delta | 无真实版本 | 旧结果追加但会更新候选字段 | 需按新合同重构不可变版本 |
| 五类行动分档 | 文案不完整 | 旧 `prefer/ask_first/avoid_now/sample_first` | 缺 `insufficient-information`，枚举需迁移 |
| 下一最佳问题 | 固定 3 问 | 主要按规则严重度生成 | 缺反事实影响和 1–3 问选择机制 |
| 回复分级与冲突 | 假复判 | 有 claims 与 evidence level | 需答非所问、冲突、不覆盖原证据 |
| 买后反馈分析 | 本地固定文本 | 无目标接口 | 必须新增 `/brew-feedback/analyze` |
| PreferenceEvidence | 无对象 | 旧长期记忆 Schema | P0 只做单次 low，不自动升级 |
| Provider 抽象 | 无 | 旧 Provider/MiMo 经验 | 可迁移接口思想，目标默认 OpenAI |
| Repository 分层 | 不适用 | 路由和服务中存在直接 SQL | 不应原样迁移 |
| OpenAPI 单一事实源 | 无 | FastAPI 可生成但旧合同已漂移 | 新 Schema 建立后生成前端类型 |
| SQL 迁移 | 无 | 单一 `init_db.sql` | 需按迁移文件管理 |
| CORS/管理鉴权 | 无 | CORS `*`，Admin 有旧鉴权 | 生产需最小域名与新 `/api/v1/admin` |
| TTL/清理 | 无 | 未见目标 15 天闭环 | 需 `expires_at` 与清理脚本 |
| 限流/费用 | 无 | 未形成目标额度 | 必须有匿名限额和调用日志 |
| 固定图片精确缓存 | 无 | 有历史测试图片/报告 | 需 SHA-256 精确 fixture 合同 |
| CI/部署 | 无项目配置 | 本地脚本为主 | 需新 Monorepo 基线后建设 |

## 5. 旧后端不宜原样迁移的具体原因

### 5.1 API 资源模型不同

旧流程以 `/compare-sessions` 和整批 populate 为中心；新流程把会话、候选、候选图片、Job、抽取版本和决策版本拆成资源。继续兼容旧接口会导致前端同时维护两套状态。

### 5.2 SQL 与业务编排耦合

旧路由中存在直接 SQL、字段白名单拼接和内部 HTTP 回调自身接口。新 PRD 明确要求 API、Service、Repository、Provider 分层。原样扩展会继续增加难以单测的耦合。

### 5.3 旧证据更新偏可变

旧商家回复会把强/中 claims 直接更新到 `tea_candidate_items`。新合同要求保留商品页证据、追加 merchant-claim、产生新 DecisionVersion，冲突不能覆盖原值。

### 5.4 图片合同不一致

旧用户图片接口要求 2–3 张整体上传，并允许 JPG/PNG/GIF/WebP；新 P0 是 1–5 个候选，每候选最多 2 张 JPEG/PNG，同候选联合、候选间隔离并行。

### 5.5 Provider 目标不同

旧项目含 MiMo 等 Provider 研发历史；新 P0 冻结为 OpenAI 默认、DeepSeek 只留骨架。P0 不应同时调试多家完整供应商。

## 6. 可迁移资产分级

### A. 建议迁移（先写测试）

- 纯文本字段归一化中的已验证边界用例；
- 规格/预算、小样/主规格、短回复回归样例；
- 候选绑定和跨候选污染的测试思想；
- 图片哈希和固定 fixture 经验；
- Scope Guard 的领域边界用例；
- 规则、答案卡和证据引用的标识符设计；
- 历史真实商品样例的脱敏 fixture。

### B. 可参考但需重写

- Provider Client；
- 图片预处理；
- 分档规则；
- 商家回复解析；
- Admin 统计；
- SQL 表结构；
- 用户记忆 Schema。

### C. 仅作历史对照

- 旧 PRD 的优先级、旧行动文案和旧 API 说明；
- 10/10、243/243 等历史通过率；
- 旧阶段报告中的“已完成”表述；
- 旧价格基线（报告明确为 draft、真实公开样本为 0）。

### D. 不应迁移

- 路由内直接 SQL；
- CORS `*` 的生产配置；
- `.env`、日志、`__pycache__`、会话 ID 文件；
- 允许模型直接决定排名的逻辑；
- 覆盖旧证据/旧决策的更新方式；
- 依赖本机绝对路径的脚本；
- 未经人工核验的 `ai_draft` 规则直接进入生产。

## 7. 数据库和知识资产的正确边界

```text
Obsidian Evidence Notes
  → 人工核验与状态确认
  → 领域规则/解释卡候选
  → 版本化 YAML/fixture
  → 后端规则与测试

Supabase PostgreSQL
  → 会话、候选、证据、任务、版本、日志

localStorage
  → P0 茶仓、泡茶日记、低置信度个人证据
```

禁止把 Obsidian 直接挂成产品数据库，也不建议在 P0 增加 RAG。感官审评五因子适用于专业品质审评，不应直接变成新手偏好分或商品推荐分。

## 8. 建议的后端最小结构

结构遵循 PRD，但阶段 1 只建立骨架和合同，不一次性实现全部智能能力：

```text
backend/app/
├── api/v1/          HTTP 输入输出
├── schemas/         唯一合同
├── services/        用例编排
├── domain/tieguanyin/ 规则、枚举、版本
├── providers/       OpenAI 与接口隔离
├── repositories/    唯一数据库访问入口
├── tasks/           TaskRunner
├── prompts/         四条独立链路
└── core/            配置、日志、错误、幂等
```

避免“屎山”的核心不是多建目录，而是强制以下依赖方向：

```text
API → Service → Domain/Repository/Provider
```

Repository 和 Provider 不反向依赖 API；领域规则不依赖具体模型；前端不依赖数据库字段。

## 9. 推荐实施顺序（待审查后执行）

1. 冻结 OpenAPI 资源与枚举；
2. 建立配置、错误模型、日志、健康检查和 CORS；
3. 建立迁移与 Repository；
4. 建立候选/图片/Job 的空实现和合同测试；
5. 接入单候选单图真实抽取；
6. 扩到同候选双图与三候选并行；
7. 建 Evidence/ExtractionVersion/DecisionVersion；
8. 再实现问题、回复复判和买后桥接；
9. 最后接部署、限流、fixture 降级和管理接口。

每一步必须先有失败用例，再迁移旧资产；不得先复制旧目录再清理。

## 10. 阶段 1 前必须确认

1. 新后端是否建立在新的 Monorepo 结构中，而不是继续把旧 `guancha-agent-v0.1` 当主线；
2. 旧后端只迁移测试和纯逻辑，不兼容旧 URL；
3. P0 数据库只存买前会话、证据、任务、版本和日志；茶仓/日记仍本地；
4. Obsidian 的 `ai_draft` 规则在进入 YAML 前需要谁负责人工确认；
5. OpenAI 具体模型、成本上限和比赛 fixture 清单；
6. 匿名客户端 ID、15 天保留和用户清除数据的合同；
7. 是否把历史真实商品样例脱敏后纳入新 test-fixtures。

## 11. 验证限制

- 本轮未启动旧后端或连接旧数据库，避免依赖未知 `.env`、写入数据库或修改历史状态；
- 未把历史测试报告当成当前执行结果；
- 已验证旧规则 JSONL、答案卡 JSONL 和抽取 JSON 可解析；
- 已完成旧路由、Schema、SQL、Provider、测试资产的定向静态盘点；
- 是否能迁移仍需在阶段 1 用新合同测试逐项证明。
