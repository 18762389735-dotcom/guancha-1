# 观茶｜项目运行说明

> 比赛体验版｜面向评委与首次体验者

## 作品简介

观茶不是替用户在全网“找一款最好喝的茶”，而是帮助用户在已经看中的 1—5 款铁观音候选中作出更稳的购买选择。用户可以先用自己熟悉的日常饮品和喝感表达偏好，再上传商品截图；系统把商品页中可追溯的信息、当前需求、真正影响选择的不确定项与商家补充信息放到同一条决策链里。它最终给出的不是“AI 保证好喝”，而是：在当前证据下哪款更接近这次需求、还应确认什么，以及新信息是否改变了结论。

## 一、访问方式

作品访问链接请以比赛提交页面中的作品访问链接为准。建议使用最新版 Chrome、Edge 或 Safari 体验；手机端最适合完整演示，电脑端同样支持通过点击左右相邻卡片或滑动查看候选差异。

## 二、推荐体验流程

### 1. 从首页开始

首次进入时，点击首页开始按钮，依次完成两步轻量引导：

1. **你平时喜欢喝什么？** 可选择茶饮、咖啡、奶与植物乳、果蔬饮品等熟悉的入口；
2. **风味与口感** 可选择自然甜感和感兴趣的风味词。

这两步只形成“感官偏好参考”，不是人格测试，也不会覆盖本次购买需求。完成或跳过后进入“添加候选”。再次进入的用户会从首页直接前往候选页。

### 2. 在候选页说明本次需求

候选页顶部的“本次需求”卡片可随时编辑。本次需求用于说明此刻最在意的方向，例如“清爽花香”“送礼”“预算 150—300 元”。系统始终优先尊重这次明确表达的需求；此前的饮品和风味选择只在解释时作为低置信度参考。

### 3. 添加候选茶与商品截图

可添加 1—5 款候选茶，每款上传 1—2 张商品截图。建议使用 JPEG 或 PNG，单张不超过 5MB；iPhone 的 HEIC/HEIF 图片在浏览器可转换时会先在本地转换，无法转换时请使用截图或导出为 JPEG/PNG。尽量覆盖商品主图、规格/价格、详情页中的茶类、香型、焙火、是否有小样或售后等信息。截图越完整，不代表结论一定更好，但能减少不必要的追问。

### 4. 开始初判并阅读结果

点击“开始分析”后，等待所有候选完成整理。每张结果卡按同一层次展示：

- **为什么它更像／不像你会喜欢**：先说明本次需求，再说明可用的偏好参考；
- **这些专业信息可能意味着什么**：将有来源的香型、焙火等信息转译为带条件的体验方向；
- **现在最值得确认**：只保留可能改变当前选择的关键未知或冲突；
- **商品页目前能确认** 与风险提示：把商品页已写明的内容和仍不能确认的内容分开。

请左右查看每张候选卡，而不要只看第一张卡或一个名次。若两款都缺乏能够区分口味方向的证据，系统会明确保留“不足以判断”的边界，而不是编造差异。

### 5. 问商家、粘贴回复并查看复判

当某个问题确实可能改变优先候选、风险或购买动作时，点击“去问商家”即可复制问题。将商家回复粘贴回来后，系统会把回复作为**商家声明**追加进本次判断，再统一复判。回复并不等于实物已被验证：专业信息回答得模糊、与页面冲突，或没有回答关键点时，结果会说明其不足并保留或继续提示应确认的事项。

复判后的“这次补充对你意味着什么”会说明补充了什么、是否改变首选或风险；如果没有改变，也会说明“结论未变”而非让用户误以为系统卡住。完成这一轮后，用户可选择具体候选并加入茶仓。比赛版提供加入茶仓和基础本地记录入口；长期饮用后的个人学习、跨设备同步不属于当前承诺。

## 三、AI如何工作

观茶把 AI 放在“读证据和理解回答”的位置，而不是让它替人断言真实口感。

1. **MiMo 多模态整理商品截图。** 它只提取截图中可见、可追溯的商品声明，例如茶类、香型、焙火描述、价格、规格或小样信息。每条内容仍保留为商品页/商家声明，而非实物检测结果。
2. **受控的专业信息转译。** 对页面明确写出的清香型、浓香型、轻焙或足火等，系统仅给出“若商品页描述准确，通常可能意味着什么”的常识方向。产地、价格、等级、“高山”“大师”“兰花香”等营销表达不能直接推出品质、真实香气或用户一定喜欢。
3. **确定性决策与安全边界。** 当前明确需求优先；风险桶、预算、试错成本和缺失关键信息由稳定规则处理。仅在安全与行动条件相同、且候选拥有明确的香型或焙火证据时，系统才可用本次的感官需求作同层级区分。
4. **商家回复参与复判。** AI 可帮助解析回复的语义，但不会把模糊回答自动当作已证实事实。系统保留初判、追加证据和复判变化，方便理解“新信息为什么改变／没有改变选择”。

因此，观茶不声称已经试喝过商品，也不做健康功效、人格化口味画像或“必然适合你”的承诺。

## 四、当前比赛版已实现

- 首次引导、首页回流与本次需求可编辑；
- 1—5 个候选、每款最多 2 张商品截图的比较流程；
- MiMo 驱动的截图结构化整理，以及面向普通用户的感官解释；
- 本次需求优先、历史偏好仅作低置信参考的个人适配说明；
- 基于反事实影响的高价值商家追问；
- 商家回复后的统一复判与变化说明；
- 候选选择、加入茶仓及基础本地记录入口；
- 手机与桌面端的候选卡浏览、加载、错误和恢复状态。

## 五、当前版本说明

当前版本聚焦铁观音比赛场景和已选候选的购买决策，不包含全网搜索、商城交易、登录账号、云端茶仓、跨设备同步、第三张及以上截图，也不把一次泡茶反馈写成永久口味档案。浏览器刷新时，如存在有效的进行中候选或判断，页面会尝试恢复该次流程；普通重新打开则从首页开始。

## 六、后续产品规划

以下为后续规划，当前比赛版未全部实现：扩大茶类范围；增加更长期、可撤销的个人感官学习；接入账户与云端同步；完善图片存储、后台队列、过期清理和更大规模的生产部署能力。这些不影响比赛版对“多候选、可追问、可复判”的核心演示。

## 七、技术与部署说明

前端采用 HTML、CSS、JavaScript；服务端采用 FastAPI；数据使用 PostgreSQL；比赛部署的多模态提供方为 MiMo，并通过 Docker/托管入口启动同源网页与 API。正式部署由环境提供端口，应用读取 `PORT`，不应把密钥或数据库连接写入前端、Git、截图或日志。

需要配置的环境变量名称如下：

- `PORT`（托管环境提供）；
- `GUANCHA_DATABASE_URL`；
- `GUANCHA_PROVIDER`（比赛部署设为 `mimo`）；
- `MIMO_API_KEY`；
- `GUANCHA_MIMO_MODEL`；
- `MIMO_BASE_URL`（如部署环境需要指定服务地址）。

## 八、本地运行（开发者参考）

本地运行需要 Python 3.11—3.14、PostgreSQL，以及已安装项目依赖的虚拟环境。以下命令只展示变量名和占位符，不应提交任何真实值：

```powershell
cd <项目根目录>
py -3.14 -m venv backend/.venv
backend/.venv/Scripts/python -m pip install -e "./backend[openai]"

$env:GUANCHA_DATABASE_URL="postgresql://<user>:<password>@127.0.0.1:5432/<database>"
$env:GUANCHA_PROVIDER="mimo"
$env:MIMO_API_KEY="<服务端密钥>"
$env:GUANCHA_MIMO_MODEL="<已配置模型名>"
backend/.venv/Scripts/python backend/scripts/run_local.py
```

默认访问地址为 `http://127.0.0.1:8000/`，健康检查为 `/health`。必须通过该本地服务地址打开页面；直接双击 `index.html` 的 `file://` 页面无法连接后端、数据库或 MiMo。若端口冲突，可在启动前设置 `PORT` 为可用端口。

## 九、常见问题

**上传后为什么没有可用结果？** 请确认后端、数据库和 MiMo 服务配置可用；本地预览只代表图片已选中，不代表已经完成分析。

**为什么已在商品页看到茶类或价格，系统还会问？** 正常情况下，已明确且可用的信息不应被重复追问。若页面只出现合并/模糊描述，或截图未覆盖完整字段，系统会把它视为仍可能影响选择的未知项；可补充更清晰的详情截图。

**为什么商家回复后首选没有变化？** 这表示新回复没有改变当前安全、预算、试错成本或可区分的口味证据。请查看复判变化说明；系统不会为了显得“有更新”而强行换第一名。

**为什么不直接说哪款一定最好？** 商品页与商家回复大多是声明，不是试饮验证。观茶的职责是降低信息不对称、提示可验证差异，而不是用未经证实的话替用户下结论。

**分析较慢、刷新后怎么办？** 多模态分析需要等待服务端完成。保持页面打开；若已有有效的进行中流程或结果，刷新后会尝试恢复。若出现服务不可用提示，请检查本地服务或比赛公网服务后重新分析。

## 十、评委3分钟快速体验建议

1. 从首页进入，完成或跳过 O1/O2；
2. 在候选页将本次需求改为“清爽花香、送礼、预算 150—300 元”等明确表达；
3. 添加两款风格不同或信息完整度不同的铁观音候选，并上传商品截图；
4. 查看每张结果卡的“像/不像”“专业信息可能意味着什么”“最值得确认”；
5. 进入问商家，观察问题为何能改变当前选择；
6. 粘贴一段有信息量或故意模糊的商家回复，查看复判变化与边界说明；
7. 选择一款候选并加入茶仓，完成“看候选—问问题—复判—选择”的完整闭环。
