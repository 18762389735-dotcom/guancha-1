# 观茶｜项目运行说明

> P0｜多候选茶购买决策助手

## 作品简介

观茶面向不熟悉专业茶语的购茶者，帮助用户在已经看中的 1—5 款铁观音候选中作出更稳的购买选择。它不以“找一款全网最好喝的茶”为目标，也不把截图识别当作产品终点；核心是把商品页和商家所说的专业信息，谨慎转译为普通人能够理解的体验方向，再结合用户这一次真实的需求，指出哪款更接近、还缺什么证据、该问商家什么，以及新增信息为什么改变或没有改变判断。

## 一、访问方式

作品访问地址请以发布页面提供的链接为准。建议使用最新版 Chrome、Edge 或 Safari；手机浏览器更适合完整浏览候选卡，桌面端也可以通过点击左右相邻卡片或滑动查看每款茶的差异。

## 二、推荐体验流程

### 1. 从熟悉的饮品开始

首次进入时，用户可以依次完成两步轻量引导：

1. **你平时喜欢喝什么？** 选择茶饮、咖啡、奶与植物乳、果蔬饮品等熟悉的入口；
2. **风味与口感** 选择自然甜感和感兴趣的风味词。

这两步只形成“感官偏好参考”，不是人格测试，也不会覆盖这一次的购买需求。已完成或跳过偏好设置的用户，再次开始选茶时无需重复完成首次偏好引导，可直接进入本次选茶流程。

### 2. 说明本次需求

候选页顶部的“本次需求”卡片可随时编辑，用来说明此刻最在意的方向，例如“清爽花香”“送礼”“预算 150—300 元”或“火味不要明显”。本次明确需求是当前判断的首要依据；此前饮品和风味选择仅作为低置信度参考。

### 3. 添加候选茶与商品截图

用户可把在电商、朋友推荐、品牌店或社交平台中已经看中的茶放入观茶。一次可添加 1—5 款候选，每款上传 1—2 张商品截图。建议使用 JPEG 或 PNG，单张不超过 5MB；iPhone 的 HEIC/HEIF 图片在浏览器可转换时会先在本地转换，无法转换时请使用截图或导出为 JPEG/PNG。

尽量覆盖商品主图、规格与价格、详情页中的茶类、香型、焙火、是否有小样或售后等信息。截图越完整，并不代表商品一定更好，但能减少无法判断和重复追问。

### 4. 初判、追问与复判

点击“开始分析”后，系统整理每个候选的商品信息并生成初步判断。结果卡会依次说明：为什么它更像／不像用户可能喜欢的方向、专业信息可能意味着什么、目前最值得确认的事项、商品页已经写明的内容，以及风险提示。

如果某个未知项确实可能改变首选、行动建议或关键风险，用户可点击“去问商家”复制问题。把商家回复粘贴回来后，系统会统一复判，说明新增信息是否改变选择。完成这一步后，用户可选择具体候选并加入茶仓。P0 提供加入茶仓与基础本地记录入口；长期饮用学习、跨设备同步不属于当前承诺。

## 三、AI如何工作

观茶采用“AI 负责理解，证据与规则负责裁决”的方式。AI 主要参与四类任务：

1. **多模态商品理解**：读取商品截图中的可见语义信息；
2. **专业信息的受控解释**：把明确的香型、焙火等专业说法转译为带边界的感官方向；
3. **自然语言理解**：理解用户的本次需求和商家的自由文本回复；
4. **变化说明**：把证据和规则产生的变化翻译成用户能理解的文字。

AI 不直接拥有最终推荐权。候选排序、风险、购买行动、版本管理和可追溯性由结构化数据与确定性规则处理。更完整的关系见下一章。

## 四、系统技术路径与核心机制

### 1. 整体技术路径

观茶采用“多模态 AI 理解 + 结构化证据系统 + 受控感官解释 + 确定性决策引擎 + 反事实追问 + 商家证据回流 + 版本化统一复判”的混合架构。AI 负责处理截图和自然语言这类复杂输入；数据与规则系统负责证据边界、硬约束、行动分档、排序、版本保存和结果复现。

```text
日常饮品与风味参考 ─┐
                      ├─→ 本次明确需求（Selection Need）
1—5 个候选茶与商品截图 ─→ MiMo 多模态理解
                              ↓
                    Extraction：结构化信息抽取
                              ↓
              Evidence：商品声明／未知／冲突与来源
                              ↓
      Sensory Interpretation：专业茶语 → 有边界的感官解释
                              ↓
       Personal Fit：本次需求优先的个体适配说明
                              ↓
   Decision Engine：风险／预算／证据充分度／试错条件／明确感官证据
                              ↓
                    DecisionVersion V1（初判）
                              ↓
     Counterfactual Question：筛选最可能改变选择的问题
                              ↓
          MerchantReply：商家自由文本回复 → Merchant Evidence 追加
                              ↓
              Aggregate Rejudge：统一复判
                              ↓
                    DecisionVersion V2
                              ↓
     DecisionDelta：解释为什么改变／为什么没有改变
                              ↓
                       用户选择 → 茶仓
```

### 2. 多模态商品理解：从读文字到理解商品声明

MiMo 处理的是商品截图中可见的语义信息，而不只是把图片转成文字。例如茶类、香型、焙火、季节、价格、规格、小样和售后/试饮相关信息，都可能成为后续判断的输入。

但模型输出不会直接成为“客观真相”。它先进入一次结构化抽取（Extraction），再作为有来源的证据使用。系统只承认“页面这样写”或“商家这样说”，不把它混同为实物检验、真假鉴定或真实试饮结论。

### 3. 证据（Evidence）：让每个判断有来源

观茶不维护一张会被后续内容直接覆盖的“最终字段表”。每条证据会保留字段、原文或规范值、来源位置、信息状态和强度。信息状态可区分页面明确写出、推断、未知或冲突；来源也区分商品页面和商家补充。

这使结果能够回答“这个判断是根据什么得出的”。例如商品页写“兰花香”，只能表示页面有这样的声明，不等于系统已验证这款茶真实有兰花香；商家后续回复也只是新增商家声明，不能无条件覆盖原页面。两者相互矛盾时，系统保留冲突，而不是静默选择一方。

### 4. 感官解释（Sensory Interpretation）：专业茶语到感官语言

证据之后并不直接跳到推荐，中间有一层受控的感官解释。它只对来源明确、与喝感有关的专业信息给出条件化说明：

- 清香型：若商品描述准确，整体通常更偏清鲜、轻扬方向；
- 轻焙：焙火存在感通常相对较低，更可能保留清鲜方向；
- 浓香或较明显焙火：可能更偏熟香、醇厚或焙火存在感方向。

这些都是“可能意味着什么”的知识解释，不是系统已经喝过该商品。产地、价格、等级，以及“高山”“大师”“兰花香”等营销表达，不能直接转化为真实口味或品质结论。文案因此避免使用“一定”“必然”“真实就是”等断言。

### 5. 个体适配（Personal Fit）：当前需求优先

首次 O1/O2 中选择的咖啡、兰花、水蜜桃或柑橘等，只是帮助用户用日常语言表达感受的低置信度参考；本次填写的“清爽花香”“火味不要明显”“送礼”等 Selection Need，才是当前决策优先级最高的输入。

系统不会把用户包装成“花香型人格”，也不展示“92% 适合度”之类的伪精确分数。它只在当前证据允许时说明：这款茶与这次明确需求更接近、较不接近，或暂时证据不足以判断。

### 6. 确定性决策引擎（Decision Engine）：AI 理解，规则裁决

最终的购买行动和候选排序不是由大模型自由生成。决策引擎综合当前需求匹配、风险、预算、证据充分度、是否能低成本试错，以及香型/焙火等明确的感官证据，形成稳定的行动分档和候选顺序。

系统内部会使用有限、离散的判断信号帮助同一行动档内的候选排序，但不会把这些内部信号包装成品质分、科学指数或口味匹配率。感官需求只能在安全边界内参与相对判断：用户偏好清香，不能让明显超预算或风险更高的候选跨越行动档，被强行排到第一。

### 7. 反事实追问（Counterfactual Question）：只问可能改变决定的问题

初判后可能仍有很多未知项，观茶不会机械要求补全所有字段。问题价值在概念上综合考虑：它对决策的影响、与当前需求的相关性、当前不确定性、商家是否容易回答，以及重复和交互成本。

系统会判断：如果这个问题得到不同回答，是否可能改变当前首选、行动建议、关键风险或试错方式；不能改变这些结果的问题价值较低，可以不问。因此，用户明确怕明显火味、而 A/B 的关键差别恰好是实际焙火方向时，询问“实际偏轻焙还是焙火感较明显”很有价值；商品页已明确写出价格时，继续问价格通常没有必要。

### 8. 商家自由文本回复（MerchantReply）：把回答变成有边界的新证据

用户不必要求商家按数据库表格回答。系统会结合原问题的语境理解“浅、深、轻、浓、可以提供、不提供、有、没有”等自然语言短回复，并区分明确回答、部分回答、模糊回答、答非所问和与页面冲突的回答。

明确回答会作为商家声明追加；部分回答只更新其中明确的部分；模糊或答非所问不会制造新事实；与商品页面冲突时会形成冲突。无论哪一种，商家声明都不会自动升级为客观事实，也不会覆盖原有 Evidence。

### 9. 统一复判（Aggregate Rejudge）：避免结果频繁跳动

系统不会在每收到一句商家回复后就局部改一次排名。它会收集当前会话中可用的新回复和既有证据，再统一运行决策，生成新的决策版本。这样能避免候选 A 先回复一句、候选 B 仍未补充时，结果因局部信息而频繁摇摆。

复判的目标是重新判断，不是强制改变第一名。新信息可能改变首选、行动建议或风险，也可能只是强化原结论；“排名不变”同样是有效的复判结果。

### 10. 决策版本（DecisionVersion）与变化说明（DecisionDelta）

每次初判和复判分别形成不可变的 DecisionVersion。典型链路为：DecisionVersion V1 → 商家回复 → 新证据追加 → DecisionVersion V2 → DecisionDelta。旧版本不会被覆盖。

DecisionDelta 面向用户说明新增了哪些信息、哪些未知得到解决、哪些风险增加或消除、首选和行动等级是否变化，以及最终为什么变化或不变化。这样用户可以回看第一次为什么这么判断，而不是只看到一张无法解释来源的最终推荐卡。

### 11. AI、规则与数据的职责边界

| 模块 | 主要职责 |
|---|---|
| AI 模型 | 商品截图语义理解、自然语言需求与商家回复理解、自然语言解释 |
| 证据系统 | 保存来源、未知、冲突与证据关系 |
| 感官解释层 | 将专业茶语转为受控、带边界的感官语言 |
| 决策规则 | 硬约束、风险、行动分档与候选排序 |
| 追问引擎 | 识别哪些未知最可能改变当前选择 |
| 版本系统 | 保存 V1/V2 与决策变化 |
| PostgreSQL | 持久化候选、证据、回复、决策版本和变化数据 |
| 前端 | 将判断过程呈现为普通消费者能够理解的界面 |

### 12. 为什么这不是 OCR 工具

即使把截图上传替换成用户手动填写相同的商品信息，观茶仍然成立：它依然可以进行专业茶语的感官翻译、以本次需求为主的个体适配、候选差异判断、高价值追问、商家回复证据回流、统一复判和 DecisionDelta 说明。

截图理解只是输入方式；产品核心是让不完整、容易被营销语言淹没的商品信息，变成可比较、可追问、可复判的购买决策过程。

## 五、当前 P0 已实现

- 首次口味偏好采集、首页回流与本次需求可编辑；
- 1—5 个候选、每款最多 2 张商品截图的比较流程；
- MiMo 驱动的结构化商品信息抽取与 Evidence 证据保存；
- 有边界的感官解释，以及本次需求优先的 Personal Fit 说明；
- 初判、反事实高价值追问、商家回复理解与统一复判；
- DecisionVersion、DecisionDelta 与复判变化说明；
- 用户选择候选、加入茶仓及基础本地记录入口；
- 手机与桌面端候选浏览、加载、错误和进行中状态恢复。

## 六、当前 P0 说明

P0 聚焦铁观音和已选候选的购买决策，不做全网搜索、商城交易、登录账号、云端茶仓、跨设备同步、第三张及以上截图，也不把一次泡茶反馈写成永久口味档案。

AI 判断建立在商品页面与商家回复提供的信息上：观茶不进行真假鉴定，不承诺识别一款茶最终的真实口感，不做绝对品质评分，商品营销声明也不会直接被当成真实饮用事实。最终购买仍由用户自主决定。浏览器刷新时，如存在有效的进行中候选或判断，页面会尝试恢复该次流程；普通重新打开则从首页开始。

## 七、后续产品规划

以下为后续规划，当前 P0 未全部实现：将茶仓扩展为长期饮茶、冲泡与真实喝感记录；对比买前预测与实际体验；形成可撤销、低置信度的 Preference Evidence 长期学习；从铁观音扩展到更多中国茶类；增加账户、云端同步、图片存储、后台队列和过期清理能力。

## 八、技术与部署说明

观茶采用前后端同源 Web 应用架构。前端使用 HTML、CSS、JavaScript，负责移动优先的交互和状态呈现；后端使用 Python 与 FastAPI，负责候选、分析任务、Evidence、Decision、Question、MerchantReply、Rejudge 和结果聚合；PostgreSQL 持久化结构化业务数据、证据、决策版本、商家回复和变化记录。

MiMo 通过独立 Provider 层接入，主要承担多模态商品理解。应用以 Docker 容器化，同一服务入口提供网页与 API。密钥只保存在服务端环境变量中，不应写入前端、Git、截图或日志。

需要配置的环境变量名称如下：

- `PORT`（托管环境提供）；
- `GUANCHA_DATABASE_URL`；
- `GUANCHA_PROVIDER`（部署使用 `mimo`）；
- `MIMO_API_KEY`；
- `GUANCHA_MIMO_MODEL`；
- `MIMO_BASE_URL`（如部署环境需要指定服务地址）。

## 九、本地运行（开发者参考）

本地运行建议使用 Python 3.11 及以上版本、PostgreSQL，以及已安装项目依赖的虚拟环境。以下命令只展示变量名和占位符，不应提交真实值：

```powershell
cd <项目根目录>
python -m venv backend/.venv
backend/.venv/Scripts/python -m pip install -e "./backend[openai]"

$env:GUANCHA_DATABASE_URL="postgresql://<user>:<password>@127.0.0.1:5432/<database>"
$env:GUANCHA_PROVIDER="mimo"
$env:MIMO_API_KEY="<服务端密钥>"
$env:GUANCHA_MIMO_MODEL="<已配置模型名>"
backend/.venv/Scripts/python backend/scripts/run_local.py
```

默认访问地址为 `http://127.0.0.1:8000/`，健康检查为 `/health`。必须通过该本地服务地址打开页面；直接双击 `index.html` 的 `file://` 页面无法连接后端、数据库或 MiMo。若端口冲突，可在启动前设置 `PORT` 为可用端口。

## 十、使用提示

**上传后没有可用结果？** 请确认图片格式和大小，并检查后端、数据库和 MiMo 服务是否可用。本地预览只代表图片已选中，不代表已经完成分析。

**为什么系统没有直接选出一款？** 当现有证据不足以区分候选时，保留不确定性并建议追问，比编造差异更可靠。

**为什么商家回复后首选没有变化？** 新回复可能没有改变安全、预算、试错成本或可区分的口味证据。请查看复判变化说明；系统不会为了看起来有更新而强行换第一名。

**为什么商品页已有信息，系统仍提示确认？** 页面中的合并或模糊描述可能仍不足以确认具体字段；补充更清晰的详情截图，或根据系统问题向商家确认。

**分析较慢、刷新后怎么办？** 多模态分析需要等待服务端完成，请避免重复提交。若已有有效的进行中流程或结果，刷新后会尝试恢复；若提示服务不可用，请检查本地服务或发布服务后重新分析。

## 十一、快速体验路径

1. 从首页进入，完成或跳过偏好设置；
2. 在候选页填写本次需求；
3. 添加两款风格不同或信息完整度不同的铁观音候选，并上传商品截图；
4. 查看“为什么更像／不像你会喜欢”“专业信息可能意味着什么”“现在最值得确认”；
5. 进入“去问商家”，复制问题并粘贴一段商家回复；
6. 查看统一复判如何说明变化或不变化；
7. 选择一款候选并加入茶仓，完成“看候选—问问题—复判—选择”的闭环。
